# Challenge the current slice across routes

Apply this built-in grill-me-style check to every engineering stage and selected specialist skill. Challenge the consequential assumptions of the current slice, using evidence and settled decisions. A clear local task can pass without a user question. Reuse answers while their relevant conditions remain unchanged; a stage or specialist change needs only its affected questions, not a restarted interview.

## Investigate, challenge, decide

1. Establish the requested outcome, current stage, accepted boundaries and relevant facts. Read available project evidence before asking the user. Distinguish an observed fact, accepted decision, proposal and unknown; investigate conflicts rather than silently choosing one source.
2. Identify the decisive assumption and one relevant failure example or legitimate exception. Check whether the accepted behavior and available evidence address it. When discussion cannot settle an empirical or visual question, propose a bounded investigation or representative prototype within existing authority rather than repeatedly rephrasing it.
3. Ask only unresolved choices that materially change behavior, acceptance, authority or costly rework. Follow dependent decisions in order and deepen a consequential answer before relying on it. Give the concrete question, recommendation, meaningful alternatives, consequences and reversibility. Batch independent questions whose prerequisites are settled; respect the user's preference for one question at a time. Do not make the user discover facts available through the project or tools.
4. Keep dependent implementation or external actions waiting for a required decision. Silence is not acceptance. Continue independent authorized work, and make low-impact reversible engineering choices under existing authority. Do not introduce another approval merely because the route changed.
5. Stop questioning when the current slice has no material unresolved decision and enough evidence for its next action. A bounded investigation can itself be that slice. Preserve accepted answers and evidence pointers in the existing task record or conversation; do not create a new questionnaire or document for every task.

Passing this check means the current decisions support proceeding. It does not guarantee that no problems remain, replace independent review or actual verification, or authorize work beyond the user's scope.

## Focus on the selected stage

Use only the relevant row and stage guide. These prompts identify consequential gaps; they are not a questionnaire to ask verbatim or a requirement to load every reference.

| Route | Challenge before proceeding |
|---|---|
| Project connection | Which maintained conventions and representative implementation apply? Where do documented rules lack actual enforcement? |
| Requirements | What user outcome and accepted example define this slice? Which exclusion, policy or success assumption remains unresolved? |
| UI | Which user task and existing design system govern the choice? What rendered or interactive evidence could expose a failed assumption? |
| Implementation | Which contracts, callers and state boundaries change? What relevant failure or recovery example would contradict the proposed repair? |
| Review | Which effective requirement and identifiable diff support the finding? Does the proposed correction preserve legitimate alternatives? |
| Verification | Which claim, artifact, configuration and environment does the check cover? What remains failed, unrun or outside its scope? |
| Release | Which artifact will reach which consumers? Are migration, recovery, acceptance evidence and execution authority sufficient? |
| Operations | What observed impact and tested hypothesis justify the next action? Which evidence will establish recovery rather than merely a restarted process? |
| Task management | Is this an existing deliverable or a duplicate? Are scope, human responsibility, execution ownership, dependencies and completion evidence clear, and are ownership controls advisory or enforced? |
| Learning | Which observed failure supports the correction? Does its safeguard reject that failure while permitting a valid nearby case, and is transfer still unmeasured? |
| Recovery | Do current artifacts agree with the handoff? Which work and live handles remain owned, and which prior decisions or checks are still valid? |

## Apply the same challenge to specialist routing

Select the minimum necessary available skills from the requested outcome, affected stack and their stated scope and exclusions. Read the selected skill before relying on it; check relevant dependencies and project conventions. A role name, advertised capability or dispatch is not evidence that its guidance was read or its work succeeded.

Challenge what the specialist adds or changes: which task does it serve, which assumption could fail, and what applicable check will establish its result? Keep the accepted outcome, file ownership, unresolved decisions and integrated acceptance with the coordinator. Specialist guidance does not silently replace a project rule, expand business behavior or grant installation, publication or destructive-action authority.

Load only the matching details. Do not recursively restart the coordinator or bounce the same unresolved choice between skills. A missing capability is a concrete gap to report or investigate within scope, not grounds to assume an unavailable skill was invoked. Return the specialist's result, remaining decisions and evidence to the active coordinator, then continue the authorized stage. This guide requires no external grill-me installation or tool.
