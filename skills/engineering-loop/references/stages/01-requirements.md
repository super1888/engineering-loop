# 01 Requirements analysis and confirmation · 需求分析与确认

## Enter

Use after the entrypoint's MCP gate when this task needs problem discovery, current-state investigation, behavior boundaries or a consequential requirement change. Classify the current deliverable, not the whole project; an accepted local change needs no renewed discovery without conflicting evidence.

## Inputs

Use the request, relevant task and existing requirement records, observed current behavior and settled decisions. Unknown product assumptions are investigation inputs, not invented requirements or automatic blockers to a bounded inquiry.

## Execution and focused references

Read [requirements.md](../requirements.md) for the applicable product hypothesis, slice, acceptance examples or change decision. Read [project.md](../project.md) only when effective conventions, authoritative sources or ownership are missing or conflicting.

For requirement intake, establish whether this is a new product or a change to an existing system. Check current behavior and retained boundaries for an existing system. If the distinction changes the investigation and remains unclear after checking available evidence, clarify it early.

Apply the [common challenge](../grill.md) at **Full depth** to a requirements deliverable: challenge whether the stated request covers the real problem before accepting its solution, and produce the written outputs, independent check and confirmation gate. A bounded fact-finding question or an accepted local change stays Light. Investigate available facts before asking; ask only unresolved choices that change the next slice's behavior, acceptance or authority. Preserve accepted answers.

## PMS

Use [pms.md](../pms.md) when a task reference, task operation or tracking policy applies. Reuse a matching deliverable; create or update only under existing authorization and policy. An exploratory question does not itself require a card. Keep the work's stage separate from its actual board status.

## Deliverables

Record the agreed outcome, scope and exclusions, representative acceptance examples, evidence and unresolved decisions in the project's existing source of truth. Link an existing research or current-state report when relevant; do not require a new document for every conversation.

Update or reference a project document or task record that covers the required content. Use the project's format when creating a new record. If a new structured record is needed and the project has no applicable format, choose a template for the current work.

- For **0→1**, use the [initial requirements record](../../templates/requirements.md) for a new product direction that needs discovery and first-slice confirmation.
- For **1→10**, use the [requirements change record](../../templates/requirements-change.md) for additions or changes to an existing system. Start from the effective baseline, identify what changes and what must still hold, and reuse relevant prior research. Investigate only the gaps that can change the current slice's behavior or acceptance.

## Exit and return

Proceed when the current slice has enough accepted behavior and evidence for its next authorized action; report material unresolved decisions and their affected work. A design-only or investigation-only request ends with that result. Enter [design and planning](02-design.md) or [development and integration](03-development.md) only when needed and authorized; do not force a full lifecycle.

Before finishing a task in this stage, follow [feedback.md](../feedback.md): append the usage line, and record any point where this skill's guidance was missing, wrong, unused or corrected.
