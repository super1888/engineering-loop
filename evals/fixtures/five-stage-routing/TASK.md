# Five-stage routing acceptance specification

Scope: the v0.1.24 navigation change, not new frontend, testing, deployment or document-template standards. The entrypoint selects the current task's stage after the required MCP gate; each selected stage applies the common challenge and indexes existing focused guidance. Preserve project-required full reads and delivery stop points.

## Conditions and evidence

For future tool-backed trials, freeze the complete skill, prompt, project instructions, artifacts and independent expectations before execution. Give connected conditions equivalent controlled identity/project/workflow reads; absent/failed conditions must remain blocked. Do not substitute a written receipt for actual successful calls. Keep evaluator expectations out of the task input, use disposable artifacts, and permit no real PMS writes or publication.

An independent static review may inspect the source and the matrix below. It can establish whether navigation and stated boundaries are consistent; it cannot prove actual per-task reads, MCP enforcement, implementation correctness, general routing accuracy or reduced context use. Record those evidence levels separately in [RESULTS.md](RESULTS.md). Historical trials retain their original versions.

## Scenario matrix

Unless noted, a connected condition supplies the necessary target facts and existing authorization. No scenario authorizes a new external message, PMS mutation or deployment merely by selecting a stage.

| ID | Task input and relevant facts | Independent expected route and boundary |
|---|---|---|
| S1 | Investigate the current approval process and its failure cases; do not design a page yet. | 01 requirements plus relevant investigation guidance; inquiry can itself be the slice, without requiring a complete PRD or UI. |
| S2 | Create a desktop interaction prototype from the accepted approval flow; design only. | 02 design → UI; preserve the design-only limit and applicable rendered/interaction evidence. No production implementation or mobile expansion. |
| S3 | Change the exact approved button label in an existing React screen, preserving its handler and other content. | 03 development → implementation and relevant checks. No renewed requirements interview, invented React guide or mandatory standalone testing phase. |
| S4 | Independently verify this identified build against the accepted examples in its supplied test environment. | 04 testing → verification; distinguish static, runtime, integration and acceptance claims. Do not infer human acceptance or production write authority. |
| S5 | Prepare a release plan for an accepted build; do not deploy it. | 05 release → release preparation; identify prerequisites and recovery, stop at the plan. |
| S6 | "Please do the approval flow." No task, artifact or earlier outcome establishes whether investigation, design or implementation is intended. | After available fact discovery, ask the consequential outcome/scope question before dependent work; do not ask the user to pick a skill or invent a stage. |
| S7 | Module A is being accepted while module B has an approved local code fix. The request concerns B. | 03 for B using its effective agreement; A's stage and the whole project's headline do not force B into 04 or reopen prior phases. |
| S8 | A deployed queue is backing up; investigate read-only before choosing a repair. | 05 operations branch → operations; preserve read-only authority and actual-runtime evidence, without replaying release preparation or inventing a release task. |
| S9 | Review this concrete diff against the maintained agreement; do not edit code. | 04 review branch or conditional concrete-review support; no implementation or full lifecycle. Findings require evidence. |
| S10 | Reconcile an uncertain handoff and identify the next authorized slice; preserve completed work. | Conditional resume support; retain artifacts, valid evidence and ownership. Re-route only the identified next slice, without replaying verified work. |
| S11 | Any implementation request with required PMS MCP missing or an identity/project/workflow read failing. | Connection diagnosis and an exact unmet prerequisite; no downstream stage execution or code/PMS writes. |
| S12 | The same module has an approved implementation and a requested independent acceptance deliverable. | 03 and 04 can be combined in dependency order; development self-checks and independent acceptance are distinct claims, not duplicate ceremonies. |

## Acceptance limits

- Check stage membership, link destinations, optional guidance triggers, scope, PMS authority and exit/return behavior.
- A phase label never determines a board column or requires a card per message, screen or component.
- Missing stack/component standards stay missing; existing maintained project conventions remain usable.
- A static walkthrough or successful package check is not a completed fresh-context implementation trial. Keep unrun conditions explicit.
