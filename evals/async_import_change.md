# Owner decision and contract change — revision 2

This is the approved owner response. Apply it to the current implementation and active contributor work. It supersedes revision 1's aggregate-only response and conflicting runtime failure descriptions. No further approval is needed for the behavior below; keep unaffected scope and validation unchanged.

1. Runtime row failures use partial success: successful rows persist and failed rows remain individually retryable. D-01's 100-row limit remains settled.
2. Every batch snapshot, including submit/retry receipts and GET results, contains `contractVersion: 2`, `batchId`, `status`, `total`, `succeeded`, `failed`, and `items`. Each item contains its original string `rowId`, `status`, integer `attempts`, and nullable `error`. Successful rows have status SUCCEEDED and error null; failed rows have status FAILED with a useful error. Items start QUEUED with attempts 0. One processor invocation increments that item's attempts once.
3. Batch status is QUEUED while accepted work awaits the worker, RUNNING while processing, then SUCCEEDED if all succeeded, FAILED if all failed, or PARTIAL if both exist. Request acceptance must not be displayed as completion. Return all row outcomes; status must agree with persisted state.
4. POST /api/batches/{batchId}/retry with a nonblank string requestId queues only currently failed rows in the same batch. Their attempts do not increment until processing. Successful row identity, output and attempts remain unchanged. Preserve failed-item error information until that item's next successful processing, when it clears. Retrying a completed successful batch is a harmless no-op.
5. A retry request identity belongs to its batch and is durable. Replaying an accepted retry requestId must not enqueue another attempt, even after processing/reopen or if that retry failed again. Concurrent retry calls or concurrent workers must not duplicate an item attempt or imported record. A distinct retry requestId may retry rows that failed again. An identical submission requestId still identifies one batch; changed payload with it remains a conflict.
6. The UI displays the real batch status and each row's identity, status, attempts and error. It offers Retry failed rows when failures can be retried. Refreshing the page restores the active batch from the server. If a retry request reaches the backend but its response is lost, the user can retry that uncertain request using the same requestId; do not silently create a new logical retry. Preserve entered rows on request failure.

Use the stable entrypoints and local test controls in SERVICE.md. Update the effective project documents and affected tests, notify active contributors of the change, and verify the combined frontend/backend behavior. Do not add deployment systems or real services.
